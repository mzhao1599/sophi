# Cloud API and agents

Owns onboarding sessions, the onboarding conversation and its recommendations, and (later) assistant runs, typed tools and the device API. For now it is a TypeScript package that the Next.js route handlers in `apps/web` call; it has no HTTP server of its own. Read [cloud agents](../../docs/subsystems/cloud-agents.md) and the [runtime blueprint](../../docs/agent-runtime.md).

**Status:** the onboarding service works with a **deterministic engine** and two stores: **in memory** (local demos, the default) and **Supabase Postgres** with row-level security, tested against a local Supabase stack but **not yet against a hosted project**. An **LLM onboarding agent** (Claude through the Anthropic TypeScript SDK, or Google's Gemini over its REST API) can read text and answer turns when it is turned on; it is off by default. It has been checked with stub models and a local mock of the API, and live on Gemini (`gemini-3.7-flash`, 2026-10-23); **not yet live on Claude**. The **walker API** (pairing, device credentials, heartbeats, the status view and answering proposals, for the always-on assistant) works with an in-memory store and **Postgres** through node-postgres, tested against a local Postgres 17 cluster; it is **deployed on Render** at <https://steady-walker.onrender.com> (free web service and Postgres 17, from [`render.yaml`](../../render.yaml)), checked end to end on 2026-10-23 (see [Walker store](#walker-store)). Its **assistant turn** (voice or text, on Gemini, with Cartesia speech) is built and checked live on Gemini with the demo's lines; Cartesia was checked live on the deployed server on 2026-10-23: a spoken question came back in Cartesia's voice, 4.1 s end to end (see [Walker assistant](#walker-assistant)).

Breaking a policy or dropping the revision check from the save function makes these tests fail (checked by hand). The `pg_cron` schedule itself was checked by hand (`select * from cron.job`), not by a test.

## How the deterministic conversation reads

Each reply is one chat message, `assistant_text`: the acknowledgement, then the next question. The engine records them as two assistant turns (the acknowledgement, then the question), so a chat page can join them into one message.

| The person | The acknowledgement |
| --- | --- |
| Taps options | The question's opener and the options in the person's terms: "Got it, knowing what's in your way and help picking things up." Openers differ by question ("Got it," "Good to know:" "Sounds good," "All right," "Okay," "Understood," "Thanks,"), so a run doesn't start every reply the same way. |
| Types only | The question's own thanks: "Thanks, that helps." for the first question, "Good to know, thanks." for places, and so on. |
| Taps options and types | The options' acknowledgement only; their words are already in the chat. |
| Skips | "No problem." |
| Skips the rest | "Sure." |

After the last answer the engine says "Here's your walker." The greeting recorded before the first question is one short sentence, and the page leaves it out.

**Covered topics.** When typed words also answer a later topic, that topic counts as answered and isn't asked: "I keep bumping into door frames at home, and a buzz in the handles would help", typed for the first question, answers places (`home`) and how to get the person's attention (`vibration_feedback`), so the next question is how to ask for help. A topic is covered (`covered_by`: the typed fact's id) only when it applies, is still unanswered, comes later in the bank, and the fact has one of that topic's tags that the fact's own topic doesn't also have: "I'd like help picking up cups" is a task (`pick_up`), so it doesn't say what to reach, and that question is still asked. `coverTopics` and `backs` in `engine.ts` hold the rule, and the agent uses the same two for the topics a model lists. Editing or removing the fact so it no longer backs a topic opens that topic again (`prune`). A covered topic can still be revisited: an answer or a skip there replaces the coverage, so it stays answered whatever happens to the words.

## Supabase store

**Choosing it.** `storeBackendFromEnv` reads three variables (listed, names only, in [`apps/web/.env.example`](../../apps/web/.env.example)):

| Variables set | Store | Onboarding |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` | Supabase | Works |
| None of them | Memory, exactly as before | Works, except in production (`NODE_ENV=production`, which includes every Vercel deployment): there it answers `503 unavailable`, because instances don't share memory, unless `ONBOARDING_ALLOW_MEMORY_STORE=true` |
| Some but not all | Memory | Always `503`, and the server log names the missing variables (never their values) |

**Tables** ([`supabase/migrations/`](../../supabase/migrations)): `onboarding_sessions` (the engine session as `jsonb`, with `revision`, `state`, `catalog_version`, `expires_at`, an owner `user_id` or a demo token hash), `onboarding_turn_results` (each turn's response, for retries; the newest 5 per session) and `device_configurations` (an account's confirmed setups, numbered 1, 2, 3… per user, never updated: a trigger rejects any `UPDATE`). There is no `profiles` table yet: confirmed facts stay in the session they came from, and are deleted with it.

**Who reaches what.**

- An **account session** is read through a Supabase client carrying the signed-in user's own access token, so Postgres row-level security decides which rows exist. Owners can read their own rows of all three tables and insert, change and delete their own sessions. They can't write turn results or setups, or delete a setup on its own: those are written only by the save function below, and a setup goes only when its session is deleted (`on delete cascade`).
- A **demo session** has no account, so the server reaches it with the secret key (service role), and every such query names `user_id is null` and the SHA-256 of the session's token. The token itself is only in the caller's cookie. The secret key never leaves the server.
- The `anon` role (any browser with the public key and no session) has no privileges on these tables, and can't call the save or expiry functions.
- Owners can call the save function and write their own sessions directly through the Data API with their own token, without this server. That can only change their own data, within the same bounds (expiry, setup numbering); the Pi must still validate any configuration it fetches against what is installed.

**Consistency.** `save_onboarding_session` is a `security definer` Postgres function, so it checks ownership itself: with no token hash it updates only the caller's own account session (`auth.uid()`), with a hash only the service role may call it and only for that demo row. It updates the session only if its stored revision still equals the one the turn started from, and writes the turn's response and, on confirmation, the setup in the same transaction. A setup must carry the owner's next number (highest so far plus one, under a per-user lock). Of two overlapping turns only one lands; the other gets `409 revision_conflict` with the current state, or, if it was a retry of the same `client_turn_id`, the stored response. Numbers can repeat after the newest setup is deleted; the device API will need its own per-device version that never goes back.

**Bounds.** A trigger caps `expires_at` on every write (an hour after now for a demo row, 30 days for an account row, plus five minutes for clock differences), and a row counts as `confirmed` only when its engine state holds a configuration, so no write can keep data longer than its notice says. Anyone can start a demo, so the Supabase store refuses a new one while 500 are live (`503 unavailable`), a conversation stops taking turns at 200 (`422`; "skip the rest" still works, so it can be saved), and only the 5 newest turn responses are kept. There is no per-address rate limit yet; add one (for example a Vercel firewall rule) before sharing a public link.

**Data handling** (AGENTS.md rule 9). Answers can reveal disability.

| | Demo session | Account session |
| --- | --- | --- |
| Consent | The start screen's demo notice (`consent.demo_data_notice`) | The account notice (`consent.account_data_notice`), only when signed in |
| Stored | Transcript, answers, facts and, once saved, the configuration, in `engine_state`; the 5 newest turn responses, for retries | The same, plus the confirmed setup in `device_configurations` |
| Kept | An hour after the last change, saved or not | Unfinished: 30 days after the last change. Confirmed: until the user deletes it or their account |
| Deleted by | **Delete my answers** (now); the `delete-expired-onboarding-sessions` `pg_cron` job every 5 minutes; the server also refuses an expired session | **Delete my answers** while unfinished; **Delete setup** in Your setups (the setup and its session); **Delete my account** there, which deletes the auth user and so every row; the same job for unfinished ones |
| Access | Server only, by token hash | The owner, through row-level security |

With the onboarding agent on, answers are also sent to the model provider (Anthropic or Google), whatever the store; see below.

## Onboarding agent

**Turning it on.** Set these on the server (for the web app, in `apps/web/.env.local`, which git ignores; see `apps/web/.env.example`):

| Variable | Meaning |
| --- | --- |
| `ONBOARDING_ENGINE` | `deterministic` (default) or `agent` |
| `ANTHROPIC_API_KEY` or `GEMINI_API_KEY` | The model provider's key, needed for `agent`. Without one the deterministic engine runs, exactly as before, and the server logs a warning. |
| `ONBOARDING_AGENT_PROVIDER` | Optional: `anthropic` (Claude) or `gemini` (Google). Unset, the agent uses Claude when `ANTHROPIC_API_KEY` is set and otherwise Gemini. Set to a provider whose key is missing, it runs the deterministic engine and warns. |
| `ONBOARDING_AGENT_MODEL` | Optional. Overrides the chosen provider's default (`DEFAULT_AGENT_MODEL` for Claude, `DEFAULT_GEMINI_MODEL` for Gemini). The model must support structured output; for Claude, also the effort setting. |

The key is read only on the server. The browser never sees it, and the first screen's notice names who reads the answers and who may keep them (`agentNoticeClause`, for example "Google's Gemini reads them to choose each question, and Google may keep a copy"). **Open before a public demo:** once sent, answers are outside this server, and **Delete my answers** can't recall them. How long the provider keeps API inputs depends on the account's terms; confirm them and say so on the first screen. With Gemini, check the key's project (Google's Gemini API Additional Terms, read 2026-10-23). On the free (Unpaid Services) tier, Google uses prompts and responses to improve its products, human reviewers may read them, and the terms say not to submit sensitive, confidential or personal information. Free-tier apps may serve only users 18 or older, and users in the EEA, Switzerland or the UK only through Paid Services. On a paid (billing-enabled) project, Google doesn't use prompts or responses to improve its products and keeps them for a limited time to detect abuse. A person's mobility needs can reveal disability, so use the free tier only with scripted, fictional answers (a rehearsed demo), and a paid key before real people type their own needs.

**What the model does, and what it doesn't.** For a `text` or `answer` turn, one model call gets the rules (the system prompt, cached on Claude) and a JSON document describing the turn: the current question, the chosen options, the user's typed words, the facts so far and each topic's status. It returns, as schema-checked JSON:

- `tags` and `declined_tags` for the user's typed words, from the `NeedTag` list only. The fact still quotes the user's own words; the model never writes a fact's text.
- `covered`: other topics those words already answered ("at home" answers places). A topic counts only under the same rule as in the deterministic engine (one of the fact's tags belongs to it and not to the current topic), and it opens again if that fact is removed or reworded so the tag is gone.
- `next`: the next topic, or `done`. It writes the question's `prompt` (48 characters at most) and `detail` **in its own words, from the topic's `purpose`** (why we ask and what a useful answer looks like). It never sees the bank's question wording, because a quotable line comes back nearly word for word; the bank's `prompt` is only the deterministic engine's (and the fallback's) wording. It picks which of that topic's **bank options** to offer, shown as small "for example" replies. It can't invent an option, so a choice always records the bank's fact and tags. It may ask the current topic once more to clarify an unclear answer, on multiple-choice topics only; that answer is added to the first one, not swapped in, and an option chosen again is recorded once.
- `ack`: one short sentence saying back what it heard, in the person's own words, or empty when the question follows straight on (then no acknowledgement turn is recorded and `ack` is `null`). It is shown with the next question as one chat message. If the person asks what the walker can do, the ack answers in one sentence from the catalog's own summaries and limitations, which are in the system prompt, or says it isn't built yet; it may not claim more, since nothing is measured. The question is open, about one thing, never two, and never lists the options.
- **Copy checks** (`copyProblem`, on the ack and the question, or the closing line, as shown): no em dashes, en dashes or ellipses; the ack doesn't open with "Noted" or "I have noted" and has no question; the prompt is exactly one question; at most two sentences in all; no internal names (tag, topic or module ids). A broken rule gets the same single retry as other rule breaks.
- `done` is accepted only when no topic is left unanswered. Ending early is the user's choice ("Skip the rest and review"), as without the agent.

Chosen options, recommendations (`recommend.ts`), the robot arms' "consider only" rule, and the review and confirm steps don't involve the model. It sees the catalog's plain-language summaries and limitations only to answer a question truthfully, never module ids or rules, and it can't pick modules. Skips, "skip the rest" and revisits stay deterministic.

**When a reply is no good.** The schema puts the tag, topic and option lists into the API request, so the model can't produce other values. The server then checks the rest: lengths, a tag both wanted and declined, a topic that doesn't apply or was already answered, a follow-up on a single-choice topic or a third ask, options from another topic, `done` with topics left. A refusal or a broken rule gets one retry with a short server note saying why (built from rule names and ids, never the user's words). A second failure, an API error, or the 15-second deadline (`AGENT_TIMEOUT_MS`) sends that turn to the deterministic engine, and the next turn tries the model again. With Claude, on a policy decline the API first retries on its default fallback model inside the same call (`fallbacks: "default"`). With Gemini, a blocked prompt or a safety finish counts as a refusal.

**Logs.** One line per agent turn: `[onboarding-agent] outcome=agent|fallback attempts=N reason=… ms=…`. No user words, ids or keys.

**Request settings.** In `anthropic.ts`: effort `low`, since a turn is a short conversational step and has to finish in a few seconds; adaptive thinking is the model's default; `max_tokens` 4096; one SDK retry. In `gemini.ts`: `responseMimeType: "application/json"` with `responseJsonSchema` set to the reply schema; `maxOutputTokens` 4096; thinking kept low (`thinkingLevel: "low"` on Gemini 3 and later, `thinkingBudget: 0` on 2.5 Flash, see `thinkingFor`); one retry on a `5xx`, and none on `429`, because a used-up quota fails again at once; a model name may be given as `models/gemini-…`. A model override that doesn't start with the chosen provider's prefix (`claude-`, `gemini-`) logs a warning at startup. Measured on 2026-10-23 over full conversations with new wording: `gemini-3.7-flash` (the default) took about 2.5 s a turn with no fallbacks, and read "at home" out of "my hallway" and "the kitchen shelf" to skip that question; with its default thinking it took about 5 s and hit the deadline on 2 of 7 turns. `gemini-3.5-flash-lite` and `gemini-2.5-flash` answered in about 1 s with no fallbacks but asked more of the questions. Errors are reported by status code only, because Google's error text can echo the request. These are starting values to tune from a live run.

## Walker store

The always-on walker assistant's server side ([walker assistant guide](../../docs/subsystems/walker-assistant.md), contract in [`walker.ts`](../../packages/contracts/src/walker.ts)). The routes are in `apps/web/app/api/v1/{devices,walkers}/` with their glue in `apps/web/src/server/walker.ts`; this package does the work.

**Choosing it** (`walkerBackendFromEnv`):

| `DATABASE_URL` | Store | Walker routes |
| --- | --- | --- |
| Set (on Render, from the Blueprint's database) | Postgres | Work |
| Not set, outside production | Memory: lost on restart | Work, for local runs |
| Not set, in production (such as the Vercel onboarding site) | None | `503 unavailable`; onboarding is unaffected |

**Tables** ([`src/walker/migrations.ts`](src/walker/migrations.ts)): `walker_devices` (owner hash, credential hash, name, last heartbeat, last manifest, last snapshot and when the server received it), `walker_configurations` (immutable versions per walker; a trigger rejects any `UPDATE`), `walker_proposals` (at most one open per walker, by a partial unique index), `walker_turns`, `walker_lines` (what the walker said on its own, from heartbeats), `walker_pairing_codes` and `walker_pairing_tries` (wrong codes by a hash of the client address keyed with a secret held only in server memory, so a stored hash can't be reversed by trying every address). Migration 0003 adds the two-phone circle: `walker_circle_members` (her own phone, at most one per walker, and caretakers, each with the SHA-256 of its `walker_member` cookie), `walker_circle_invites` (6-digit codes, 10 minutes, one use) and `walker_circle_messages` (30 characters, deleted 24 hours after sending, and with either phone by cascade; past a walker's newest 20 a message is cleared, its text deleted and a short record kept until its 24 hours end, so a retried send isn't saved again). The walker's own sweep (server start, heartbeats, page reads) also deletes the circle's expired rows, at most once a minute per process (`sweepCircleThrottled`). Wrong invite codes go in `walker_pairing_tries` under an address key of their own, so they share pairing's limits but not its count. The migrations run at server start (`apps/web/instrumentation.ts`) in one transaction holding a Postgres advisory lock, so two instances starting at once never race; each runs once, recorded in `walker_schema_migrations`.

**The circle in SpacetimeDB.** With the four `SPACETIME_*` settings, `walkerBackendFromEnv` wraps the store in `SpacetimeCircleStore` ([`src/walker/spacetime-store.ts`](src/walker/spacetime-store.ts)): the circle's steps go to the care-db module's procedures ([`services/care-db`](../care-db/README.md)) and the circle tables above stay empty; everything else is unchanged. [`src/walker/care-db.ts`](src/walker/care-db.ts) reads the settings, signs the tokens and calls the procedures. Its tests: `SPACETIME_TEST_SERVER=http://127.0.0.1:3010 pnpm --filter @walker/cloud-api test` with a local `spacetime start --listen-addr 127.0.0.1:3010`.

**Who reaches what.** The server is the only database client: there's no Data API, so Supabase-style row-level security doesn't apply. Ownership is enforced in every query instead. The Pi's walker is found only by the SHA-256 of its credential, and the page's only by its id together with the SHA-256 of the `walker_owner` cookie; everything else is read and written by the device id found that way. An unknown id and someone else's both answer `404`.

**Opt-in GPS extension (software written, receiver unverified).** Migration 0004 adds a sharing flag, one current fix, and its receive time to `walker_devices`. Only an approved `walker_user` member cookie can enable sharing; a caregiver or waiting member cannot. A fix in a device heartbeat is stored only while sharing is on, and a simulator's fix is ignored. Turning sharing off or removing her phone atomically clears the fix. Caregivers see it only while the walker is online and the fix is at most 60 seconds old; her own phone gets the switch state without coordinates. The old fix is deleted on the next server sweep. Neither model turns nor ordinary logs receive coordinates. The Pi must have a configured USB serial GPS receiver; no real fix has yet been checked.

**Consistency.** Each step that must be atomic is one transaction that first locks the walker's row: answering a proposal (so of two Confirms at once the second sees the first's result and gets `409 proposal_closed`), saving a turn with the proposal it opens, and claiming a pairing code. A claim first locks its client address (a second claim from that address at the same moment gets `429 rate_limited` at once, rather than hold a connection while it waits), then counts that address's wrong tries, checks the code and records a wrong one, all in one transaction, so tries sent at once can't get past the lockout; it also locks the owner, so two claims can't both pass the 8-walker limit. The lockout window slides: it lifts 10 minutes after the oldest of the 5 wrong tries. The in-memory store makes each of those steps with no `await` inside it. Both stores call the same rules ([`rules.ts`](src/walker/rules.ts)), and both run the same tests.

**Data handling** (AGENTS.md rule 9):

| | |
| --- | --- |
| Stored | The walker's name, its configurations, its last manifest and sensor snapshot, proposals, turns (what the person said, as typed or transcribed, and the reply) and the walker's own lines. While GPS sharing is on, one latest fix only. Only the SHA-256 of the owner cookie and the device credential, and a keyed hash of a wrong-code client address. Never a voice clip. A NUL character or half a surrogate pair in any text becomes U+FFFD, since Postgres can't store them |
| Kept | Turns, walker lines and answered proposals: an hour after they happen, deleted on every heartbeat, every page read and at server start. Pairing codes: 10 minutes. Wrong-code tries: 10 minutes. A GPS fix is displayed for at most 60 seconds and deleted on the next sweep, immediately on opt-out or removal of her phone. The walker itself, its configurations and its last manifest and snapshot: until Forget |
| Deleted by | **Forget this walker** on the page (`DELETE /walkers/{id}`): one statement, so one transaction, removes the walker and, by cascade, everything about it, and its credential stops working. The sweep above |
| Access | The server only, by device id found through a credential or an owner, as above |

**The page's activity log** ([`src/walker/activity.ts`](src/walker/activity.ts)). For the /walker page's live companion, `GET /walkers` also returns `activity`: per walker of that owner (the ids come from the owner's own walkers, never from the log), the turns in flight and a trace of each recent saved turn. It is not in the database: one `ActivityLog` per server process, kept on `globalThis` by `sharedWalkerActivity()` (every route builds its own `WalkerService`, and Next.js bundles routes separately), so a restart empties it, and with more than one server instance each would have its own. A turn shows in flight once its clip or text is accepted (after the replay and WAV checks), as `hearing` during the model and `voicing` while Cartesia is asked, and is cleared in a `finally` however the turn ends; two uploads of one `client_turn_id` share one entry until both end. A trace is written only when a turn saved a new row (never a replay): `model_ran`, `model_ms`, `rule` (the reason code above, such as `arms`, `cues_alerts_off`, `timeout`, `no_model`; null when the model's own words were used), `answered_by`, `proposal_opened`, `voiced_by`, `voice_ms` (null when Cartesia wasn't asked), `clip_ms` (from the WAV's samples), `total_ms`. Bounds: at most 4 turns shown in flight and 10 traces a walker, none older than an hour; Forget deletes the walker's entry at once. No words, transcripts or replies are ever in it.

## Walker assistant

One question and its answer (`WalkerService.turn`, routes `POST /devices/{id}/turns` and `POST /walkers/{id}/turns`).

**Tool loop (implemented, not yet checked on real GPS).** Gemini selects `get_distance`, `get_location` or `get_weather` in a schema-checked `tool_call`; no keyword match executes them. The server computes distance from validated zones. Location and current weather need the Pi: the server returns an unfinished response with `tool_call`, and the Pi reads GPS and calls the provider before repeating the request with the same `client_turn_id` and accumulated `tool_results`. The next model step can request another tool or answer. At most eight results are accepted; an exhausted budget ends with a fixed line. Only the final answer and any Confirm-gated alert proposal are stored. Raw GPS coordinates never enter these turn requests, though the Pi's location description and weather summary do go to Gemini so it can reason over them. An unfinished response's `turn` is a temporary envelope for the Pi, not a saved conversation turn. The "I'll check" line comes from one record over every tool name (`LOOKUP_LINE`). A continuation of a spoken turn (`original_audio`) is described to the model as spoken, so it never answers it as typed. See [the walker assistant guide](../../docs/subsystems/walker-assistant.md#how-a-spoken-question-travels).

**Walking directions (built 2026-10-24, cloud side only).** A walker turn carrying `navigation` is offered `start_route` (with `destination`, bounded by the contract's `RouteDestinationSchema`) and `stop_route`, in the schema (`WALKER_ROUTE_REPLY_JSON_SCHEMA`) and the prompt (`walkerSystemPrompt("tools")`); its context gets `walking_directions`, the Pi's `RouteSummary` or null. Other turns get neither tool: an older walker keeps "can't navigate" (`"none"`), and the page is told directions work only through Talk (`"page"`). The response's `tool_call` carries `destination` through to the Pi. At most one route tool per turn: once `tool_results` holds one, another tool request isn't run (fixed line, reason `route_once`). A route tool the server didn't offer: `route_unavailable` on a walker, `device_tool_only` on the page. The Pi runs the tools ([navigation guide](../../docs/subsystems/navigation.md)).

**Messages.** `send_message` is a terminal model tool proposal, limited to an approved caregiver in the walker's Circle and a 30-character text. The server returns `message_offer` with an idempotency ID but does not send. After the Pi reads the draft and gets a fresh left Confirm press, `POST /api/v1/devices/{id}/messages` revalidates both phones and saves the message through the Circle store. The Pi gives an uncertainty notice if the POST times out, since a retry might duplicate the user's intent even though the ID prevents a duplicate row. Incoming messages are never model context. `incomingMessages` (`GET /api/v1/devices/{id}/messages`) gives the paired Pi the newest 5 messages an approved caretaker sent to her phone, as `{message_id, from_name, text}` only, for the walker to read aloud in its own voice; it reads the Circle store and nothing else. This is in-app Circle messaging, not SMS, and has not yet been tried on the physical Pi.

**Typed turns on Claude (built 2026-10-24).** A turn the person typed (on the walker's page, or text from the walker with no `original_audio`) goes to Claude when `ANTHROPIC_API_KEY` is set (`walkerTypedAssistantFromEnv` in `config.ts`): `claude-opus-5-5` at low effort through the onboarding adapter (`WALKER_TYPED_MODEL` overrides it; `WALKER_TYPED_PROVIDER=gemini` keeps typed turns on Gemini). Same prompt, schema, rules, one retry and 8-second deadline as Gemini; no backup model. A spoken turn, and the text continuation of a spoken turn after a tool (`original_audio: true`), always stays on Gemini, so one turn never switches model (`WalkerService.assistantFor`). The page-only activity view says which model ran (`model`: `claude` or `gemini`) on each in-flight entry and trace, and the page names it; the turn views the Pi parses are unchanged.

**The model for spoken turns.** Always Gemini (`GEMINI_API_KEY`), whatever the onboarding provider is, because voice turns need audio input. Two models are asked at the same moment (`hedge.ts`): the main one, `gemini-3.7-flash` with low thinking (`WALKER_AGENT_MODEL` overrides it), and a backup, `gemini-3.6-flash` with minimal thinking (`WALKER_BACKUP_MODEL`; `none` turns it off and asks one model, as before). The main model's answer is used unless it hasn't come 4.5 s after the start (`WALKER_BACKUP_AFTER_MS`, at most half a second before the turn's own limit); from then on the first usable answer wins, and the backup's is usually ready. If the main model fails early, the backup's answer is used at once; a refusal from the main model is final; if both fail, the fixed line below answers, with the reason of the one that failed last (what the person waited for). The other attempt is cancelled once an answer is picked, so it can't start a retry. The turn's model time is the time to the pick, which is what the person waited, and the log line names the model that answered. Every rule below applies the same way to either model's answer. A voice clip goes to Gemini as `inlineData` (`audio/wav`) in the same `generateContent` call as the JSON schema; a live check on 2026-10-23 returned the exact transcript with the reply. The model sees, in order: the policy (the system prompt), the walker and how the person asked, its configuration, its parts with health and `simulated`, its zones (measured, with the reading's age already worded the way it's said, `reading_age`: "just now" under a second, then whole seconds such as "3 seconds ago", never milliseconds; or unknown), the suggestion waiting for Confirm, the last 10 turns, and the person's words, as data. A walker's turn uses the snapshot it carries, received now, instead of the heartbeat's. The reply is `{ transcript, reply, topics, cues_change }`; a reply over 350 characters, one off the schema, or one that says "clear" or "safe" (see the rules below) is retried once with a note naming the rule (never the person's words).

**The server's rules,** all from structured fields, never from the words:

| When | What the server does |
| --- | --- |
| `topics` has `arms` | The reply is a fixed line from the manifest ("This walker doesn't have robot arms…"), `answered_by: "fixed"`, and any change is dropped. No action request exists |
| A `cues_change` fails `checkCuesChange` | Dropped; the reply is a fixed line saying why, `answered_by: "fixed"` |
| A valid `cues_change` while the walker is offline | No proposal; a fixed line says the walker is offline |
| A valid `cues_change` | A proposal opens: summary written from the payload ("Switch your alerts from buzzing to short sounds."), the turn's `client_turn_id`, 60 s to answer. The reply is written from the same payload ("I can switch your alerts from buzzing to short sounds. Press Confirm to do it."), so the person hears exactly what Confirm will do, never the model's description of it; it stays `answered_by: "model"`, since the model chose the change |
| A proposal is already open | The reply gets "Still waiting for you: … Press Confirm to do it." |
| The reply says "clear" or "safe" in any form ("cleared", "clearance", "safer", "safety", "safely", "unsafe"; "clearly" passes), even to deny it, and the server would speak the model's words (no `arms`, no `cues_change`) | Rejected like a broken reply: one retry with a note naming the rule; a second such reply gets the fixed line. A sensor can miss things. A word list can't catch every way of saying it ("nothing ahead", other languages); the policy asks for the rest. Live on 2026-10-23 (local runs, not in the repo): on the demo's lines, `gemini-3.6-flash` said "I cannot say if the way is clear" on 9 of 210 obstacle answers and `gemini-3.7-flash` never did, and no other answer of 419 used these words. Asked outright ("Is the way ahead clear?", "Is it safe to walk forward?"), both models used them on most first tries: 3.6 alone, 12 turns, all retried, 11 fixed by the retry, 1 fixed line; with the backup on, 12 turns, answers in 3.9 to 5.8 s, 11 by the model, 1 fixed line at 8 s. So the guarantee costs time on such questions (`saysClearOrSafe` in `assistant.ts`) |
| `topics` has `obstacles` and a ToF part is simulated | The reply gets "These readings are simulated." |
| `topics` has `parts` and a reported part is simulated (and the line above didn't apply) | The reply gets "All of this walker's parts are simulated." when every part the walker reports is (as on the simulator), otherwise "Some of this walker's parts are simulated." The policy tells the model the server adds the "All" line itself, so the model leaves it out (it said it in 5 of 5 live answers before, 0 of 5 after, 2026-10-23); this rule, not the model, is the guarantee |
| An error, a refusal, a bad reply twice, 8 s, or no key (with the backup on: the main model refused, or both models failed) | A fixed line from the status view, `answered_by: "fixed"`; a voice turn with no transcript has `heard: null` |

The model can't confirm anything: only Confirm by id changes a walker (piece 2). A turn's response reads its proposal after expiry, so a replay of an expired proposal, or a walker that dropped offline while the model answered, never comes back as `open`. The rules are one pure function, `applyRules` in `service.ts`.

**Time.** The Pi gives each cloud step 10 s, and a GPS read can take up to 20 s between steps; Talk can cancel the whole pending turn. Each server request, counted from when the route starts reading it, stays within 8 s: one model step gets at most 8 s and only the time left in that request, then voice gets at most 3 s and only what's left (skipped under half a second). A multi-tool turn uses several requests and may take longer than one answer.

**Idempotency.** A `client_turn_id` already stored returns that final turn and its proposal with a fresh status and `speech: null`, without calling the model. An unfinished tool request is not stored, so a retry may rerun a read-only tool step; no proposal or physical action can occur before the final turn. Two final uploads of one turn at once store one turn and at most one proposal (the store's `saveTurn` is one transaction).

**Speech.** With `CARTESIA_API_KEY` (not `none`), a walker turn's reply text goes to Cartesia (`POST https://api.cartesia.ai/tts/bytes`, `Cartesia-Version: 2026-10-23`, model `sonic-3.6`, the stock voice "Skylar" unless `CARTESIA_VOICE_ID` names another stock one, 16 kHz mono 16-bit WAV; the 2026-10-23 version label has not been checked live). It returns as `speech` and the turn is `voiced_by: "cartesia"`. With no key, an error, more than 3 s (or less of the turn's 8 s left), audio over `SPEECH_MAX_BYTES`, or audio the Pi's player can't play (anything but PCM 16 kHz mono 16-bit with samples), `speech` is null and `voiced_by` is `"walker"`. Page turns are never spoken. The paired Pi can also request this voice for one of its own short lines through `POST /devices/{id}/speech`; the route authenticates the device, calls Cartesia, and creates no conversation turn. The Pi falls back to local speech on failure. On 2026-10-24, the paired Pi received a 200 response with audio from the deployed route; a listening comparison remains to be done.

**Measured** (live on `gemini-3.7-flash`, 2026-10-23, 30 turns a run: the demo's lines 3 of 3 typed and 3 of 3 spoken, plus 3 fresh wordings each way, on a walker reported the way devices/pi's simulator reports it, including `base.walker` (`sim-coordinator`, added in #36); without it, a "which parts work?" turn heard that the walker itself wasn't responding): every check passed and every voice transcript was exact, at a median of 2.5 to 3.7 s and at most 6.8 to 8.0 s a turn over five runs. To run it again (a Mac with `say` and `ffmpeg`; the clips are written to a temporary folder and never played):

```bash
WALKER_LIVE=1 pnpm --filter @walker/cloud-api walker-live
```

The suite builds the assistant from the same settings as the server (`walkerModelsFromEnv`), so it runs with the backup unless `WALKER_BACKUP_MODEL=none`.

**Walking directions, measured** (2026-10-24, `gemini-3.7-flash` with the `gemini-3.6-flash` backup, spoken as synthetic `say` clips on a walker sending `navigation`; the Pi's tool results are fixed text in the harness, so no GPS, map service or Pi was involved). The six lines "Take me to the Lake Merritt Boating Center", "Can you give me walking directions to the library?", "How far is it now?" (with a route summary of 620 m and 9 minutes, simulated), "Stop the directions" (route on), "Where am I?" and "Pick up the cup", three runs each, twice with the final prompt: the model picked `start_route` (destination "Lake Merritt Boating Center" or "the library"), `start_route`, no tool (answering 620 metres, about 9 minutes, and saying the position is simulated), `stop_route`, `get_location` and the arms line on every turn it answered. One turn of 36 ("Take me to ...", first step) hit the 8 s deadline and got the fallback line; every other check passed. To run it alone:

```bash

```

**Why the backup** (measured live on 2026-10-23, the suite above with both models' answers logged on every turn): `gemini-3.7-flash` alone, 120 turns: median 3.07 s, 90th percentile 5.80 s, one 8.0 s timeout (the alert-change line, spoken), which got the fixed line. With a prototype of the backup at a 5 s switch-over, 210 turns: median 3.09 s, 90th percentile 5.00 s, slowest 5.0 s, no fixed lines, every check passed; 3.6 answered 26 turns, all correct, including a real 3.7 timeout; it answered all 210 within 3.3 s and named the right alert change on 56 of 56 alert-change turns. Running both didn't slow 3.7 (median 3.09 s, 90th percentile 5.30 s), and there were no quota errors. Replayed on the same calls, a 4.5 s switch-over would have used the backup on 33 turns with no bad answer used, and leaves the voice its full 3 s; at 4 s one bad answer would have been used. The built version at 4.5 s, two live runs of this suite (2026-10-23): 60 of 60 checks passed, slowest 4.51 s, the backup answered 12 turns (7 of them on the alert-change lines), all correct. Not proven by the suite: the Pi, the voice and Render's network. One known 3.6 habit: on "Is anything in front of me?" it sometimes denies in the forbidden words ("I cannot say if the way is clear", 9 of 210); 3.7 always answered that line in time, so none was used.

**Data.** The person's clip goes to Gemini with the turn and is then dropped: never stored or logged. Their transcript or typed words and the reply are stored as the turn (an hour, as above), and the reply text goes to Cartesia when speech is on. With the backup on, the clip and context go to both Gemini models (the same provider and terms). Logs carry one line per turn: ids, who answered, why not the model, attempts, which model answered, model and voice milliseconds, whether a proposal opened. Never words or audio. The expected results are in [`test/walker/EXPECTED-turns.md`](test/walker/EXPECTED-turns.md).
