# Web app and onboarding guide

**For:** the web developer, designer, and onboarding agent developer. The proposed home is `apps/web/`; the agent implementation may live in `services/cloud-api/` or server-only Next.js code.

## What to build

The web app has four primary areas: (1) onboarding chat, (2) review and edit a module recommendation, (3) pair and view a walker, and (4) change preferences and privacy settings. It should feel polished through good type, clear hierarchy, responsive layout, and useful feedback. Accessibility is part of the experience, not an optional theme.

### Onboarding sequence

1. Explain what the prototype does and ask for data/microphone consent separately. Offer a text-first path and a demo mode that avoids saving sensitive details.
2. Ask one focused question at a time about a task, environment, and preferred feedback. Examples: “What would you like help doing while using the walker?” and “Would a spoken cue or a vibration be easier to notice?” Do not require a medical diagnosis or force a user to disclose one.
3. Show an editable running summary labeled “What I understood.” Distinguish facts the user said from assistant inferences. Let users correct or remove entries.
4. Recommend only catalog modules that match a stated need. Show a reason, prerequisites, limits, and why a lighter alternative might suffice. Let the user add/remove modules manually.
5. Confirm the configuration and explain that hardware availability and bench checks determine what can be enabled on the actual device.

The onboarding agent does not silently change a confirmed configuration. A later change shows a diff and requires confirmation. If information is insufficient, ask a concise follow-up or say that the recommendation is uncertain. Avoid overclaiming what ToF, GPS, or manipulation can do.

## Accessibility requirements

Target [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/). Implement semantic headings, landmarks, real buttons/labels, keyboard operability, visible focus, logical tab order, readable contrast, scalable text, no information conveyed by color alone, and sufficient target size/spacing. Every voice interaction has a text equivalent; every important sound has visible text, and useful haptic/visual alternatives should be considered on device. Streaming chat updates should announce meaningfully through a controlled live region without reading partial tokens constantly. Keep motion subtle and honor reduced-motion preferences. Do not auto-start microphone capture.

Test with keyboard only, browser zoom, at least one screen reader, a mobile viewport, and a user or teammate who does not know the flow. An automated accessibility check is useful but cannot replace those checks. The UI should make slow agent responses, retries, errors, and offline/device-unavailable states understandable.

## Suggested page map

| Route | Purpose |
| --- | --- |
| `/` | The demo, one page: a guided chat beside a live drawing of the walker, then the clickable walker to adjust, save and order (built) |
| `/onboarding`, `/onboarding/review` | Redirect to `/` (they were the separate conversation and review pages) |
| `/walker` | **Your walker**: pair a walker, watch it live, read and join its conversation, confirm or decline what it offers (see below) |
| `/devices` | Paired devices, online/last-seen state, actual modules |
| `/devices/[id]/settings` | Audio/haptic preferences, privacy, caregivers if later supported |
| `/devices/[id]/activity` | Human-readable action and fault history |

Do not show a module as “installed” merely because it was recommended. Distinguish `recommended`, `selected`, `installed`, `healthy`, and `enabled` in UI and API state.

## Your walker page

`/walker` is the owner's page for the always-on walker assistant ([guide](walker-assistant.md)), separate from the onboarding demo on `/`. It talks only to the owner's routes in [`walker.ts`](../../packages/contracts/src/walker.ts) (`/api/v1/walkers/...`, proven by the `walker_owner` cookie) through one interface, `WalkerPageApi` in `apps/web/src/lib/walkerApi.ts`, so a development fake (`walkerFake.ts`) can stand in for the server. The expected results it is tested against are in `apps/web/test/walker-page.EXPECTED.md`.

- **No walker:** "Connect a walker" asks for a pairing code and shows it large with a countdown and the command to run on the walker (`walker pair <code> --server <this site>`). The page switches to the walker as soon as a poll lists it.
- **Paired:** the walker's name, Online or Offline with "last seen", a Simulator badge when the whole walker is the simulator, and the pen-drawn walker with each reported part lit by what the walker says now: solid green only for a real, healthy part, dashed green and the word "Simulated" for a stand-in, a dotted outline and "Unavailable" when it isn't there. Under it, the alert settings ("Applied" only when the walker reports the current configuration version, "Waiting for the walker" until then) and the obstacle zones (a distance with its age, or "Unknown" with the reason; never "clear").
- **Conversation:** turns and the walker's own lines, oldest first. Each says who heard it ("You said (as heard by Gemini)", "You typed", or "Sophi didn't catch that"), notes when the fixed replies answered, and names the voice the server offered (Cartesia's or the walker's own). A typed question goes to `POST …/turns` with a fresh `client_turn_id`; the same words retried after a failure reuse it. The notice about Gemini, Cartesia and the hour's retention is on screen above the box before anyone types.
- **Offers:** the open proposal as a card with the server's summary, what changes, a countdown, and Confirm and Decline. Once closed, the buttons give way to one line saying how (from the server's answer, or, when it closed elsewhere, only what the status proves).
- **Behind the scenes:** under the conversation and the walker, the latest turn drawn as a survey traverse: a trig point per step, inked by a pen as that step's evidence reaches the page. The steps: what was sent (a clip's length, or typed), Gemini (its measured time; drawn only when the model ran), the rule that decided the reply in plain words ("Gemini's own words", "Fixed line: no robot arms", "Refused: alerts keep a buzz or sound", "Fixed reply"), the reply (an offer is "written by the server"), the voice the server *sent* (never "spoke"), and for an offer: waiting for Confirm, "Button press, not voice", "Recorded v2", then "Applied" once the walker reports it. While a turn is in flight it shows "Hearing: waiting for Gemini…" or "Voice: waiting for Cartesia…". The data is the list response's page-only `activity` (`WalkerActivityViewSchema`), which the server keeps in memory; without it (after a restart, or an older server) the panel draws only what the status view proves and says "No timings for this turn". The logic is `src/lib/behindTheScenes.ts` (unit tested); the times printed are the server's, never the page's.
- **Forget this walker**, behind a modal confirm.
- **Live:** polls `GET /api/v1/walkers` every 1.5 s while the tab is visible, and every 0.7 s while a poll lists a turn in flight (less than 10 s old); back to 1.5 s on any failure. After 5 s without an answer it says so, shows "Status unknown" and turns every zone "Unknown", so old readings never sit on screen looking current. Every error code has a plain sentence.
- **Accessibility:** one polite live region reads each new reply, walker line, offer and connection change once (never the history on load, never the countdowns); every control is a real button, input or select with a name; focus follows the person's action when the pressed control goes away; the drawing is hidden from screen readers and described in words; reduced motion stops the pen and the contour field.
- **Checked (2026-10-23):** a headless Chromium script drove `/walker?fake=1` by keyboard alone through pairing, a reply, an offer confirmed and one expiring, offline, the server going down, each error code and Forget (55 of 55 checks), then checked 390 px wide and 720 px (200% zoom of 1440) for sideways scroll and cut-off controls, and reduced motion (no pen, the frame drawn at once). Against the real routes and the Pi simulator, see the [walker demo rehearsal](../demo/walker-script.md#rehearsal-results). Not yet: VoiceOver or NVDA.
- **Checked, Behind the scenes (2026-10-23):** headless Chromium on `next dev` with `/walker?fake=1` (the fake is development only): a spoken ask, an offer confirmed on the page through "Applied", and the arms question typed, at 1440 x 900 (the whole page fits one screen without the development banner), 390 px (the steps run down the page), 720 px (200% zoom), reduced motion and forced colours; the panel's accessibility tree; Tab reaches it. Not against the real server's `activity` yet.
- **Development fake:** `/walker?fake=1`, in development only, uses the fake, shows a "Fake walker" banner across the top, and adds a "Fake walker controls" panel to pair, speak a walker line, press Talk with one of the script's lines (an audio turn in flight, then saved with a trace), go offline, press Confirm on the walker, expire the offer, take the server down, and make the next action fail with any error code.

## The two-phone app (/app)

Two real phones held up on stage: Rose's (the person who walks with the walker, role `walker_user`) and Maya's (a caretaker, `caregiver`). One web app at `/app`, added to each phone's Home Screen as "Sophi" (its own manifest, scoped to `/app`; Apple's Home Screen tags; PNG icons drawn from the mark; no service worker). Shapes are the "two-phone app" section of [`circle.ts`](../../packages/contracts/src/circle.ts). All server calls go through one file, `apps/web/src/lib/phoneApi.ts` (`PhoneApi` for the phones, `OwnerPhonesApi` for the owner's page), so the in-memory fake (`phoneFake.ts`) can stand in for tests and `?preview=`.

- **Join:** "Link this phone to a walker": a 6-digit code typed on a big numeric keypad (`inputmode="numeric"`, `autocomplete="one-time-code"`), with the data notice under the button. Her own phone is in at once. A caretaker's phone waits ("Waiting for the family to approve") until the owner's page approves it with the consent line; it never waits for a press on the walker. Not approved in time reads "Not approved yet. Ask again later."
- **Rose's phone, simple mode** (built the Assistive Access way): four huge tiles (Get help first; see "Asking for help" below), one action each, no typing and nothing that changes the walker. **My walker**: "Your walker is on." and "Alerts: short sounds and spoken messages." in sentences, plus "Nothing on this phone changes your walker. To change your alerts, ask Sophi on the walker." **Message Maya**: the newest message from Maya set large; tapping it reads it aloud with the phone's own voice (`speechSynthesis`, only on her tap; where the browser can't speak it's plain text, not a dead button); three one-tap replies ("I'm okay", "Can you call me?", "I'm on my way"); "Sent to Maya: I'm okay" shows only after the server's 201. **People nearby**: the sample on a map, below. A "1 new message" line on the tile is kept on the phone only (the server has no read state).
- **Maya's phone:** three sections. **Walker**: "Rose's walker", Online or Offline with a filled-and-ringed or hollow dot and the word, a Simulator tag when it is the simulator, the alerts in force, part health (with Simulated tags), "Battery: not measured on this walker", and a recent GPS fix only after Rose enables sharing on her own phone. **Messages**: the thread ("You" or "Rose" on each), a labelled box with a "0 of 30 characters" counter (code points, as the server counts), "Rose's walker reads your messages aloud." under it (both tied to the box with `aria-describedby`), Send. The walker reads each message to her phone aloud in its own voice ([interfaces](../interfaces.md), "Her incoming messages, read aloud"); the join notice and the owner's consent line say so. **Nearby**: the sample, with other caretakers too. No "Suggest an alert change": the server has no route for one, so there is no button. Never her conversation or activity history.
- **People nearby is a sample on a real street map,** a fixed fixture in the app (`src/lib/nearbySample.ts`): made-up people, walking groups and step-free places, each pinned at a fixed made-up point around Lake Merritt, Oakland (`SAMPLE_AREA`). The map (`NearbyMap.tsx`, Leaflet 1.9.4) draws OpenStreetMap's own tiles (no key; light use under its tile usage policy, with its attribution) and numbers each pin like its card in the list under it; people are filled circles, groups filled squares, places hollow circles, and a ringed dot is the sample's starting point. Distances are computed from that starting point, never from the phone or the walker. Only tiles for that fixed area are fetched, so the tile server learns nothing about anyone's position (it does see the phone's IP address, as any web request does). The list stays the full path: every pin's name and description is on its card, pins are keyboard buttons that open the same text, one-finger drags scroll the page on touch screens, the map's animations are off under reduced motion, and dark mode inverts the tiles. The heading carries a dashed "Sample" tag and says that nothing here uses GPS or anyone's real location. The site's Permissions-Policy still blocks browser geolocation; the optional walker receiver is a separate path. Checked 2026-10-24 in the browser pane at 390 x 844, light and dark, on `/app?preview=rose` and `?preview=maya`: tiles load, pins sit on land, Enter on a focused pin opens its popup, each pin has its label, no console errors. ## Data handoff

Use the session/turn API in [interfaces](../interfaces.md). The UI sends a turn with a revision and renders both assistant text and structured recommendation updates. It treats the model's profile patch as a suggestion until the user reviews it. When the user confirms, persist a versioned configuration; the Pi separately reports physical capabilities. Prefer server-rendered authenticated pages for private settings and keep privileged keys server-side.

For an optional “call the onboarding agent” integration, expose the same session/turn flow through a narrow authenticated API and a machine-readable description. A caller starts a session, sends a user-provided message, reads structured recommendations, then asks the user to confirm. It cannot impersonate a user, bypass consent, or auto-confirm modules. This is a planned interface, not a live endpoint today.
